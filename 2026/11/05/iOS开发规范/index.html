iOS开发规范

2026/11/5 编程 iOS

一：命名规范

通用命名规范

  1. 清晰简洁性：可读性高，意思明确。通过：removeObject:，不通过：remove:（不明确移除什么）。命名要尽可能的清晰并简洁，如果两者不能兼得，则以清晰为主。

  2. 杜绝中文命名和数字命名。

  3. 一致性：相同类型或者具有相同作用的变量的命名方式应该相同或类似。正例：NSDictionary、NSArray、NSSet 这几个集合类都是用 count 来表示数量而不是一个用 count 其它的用 amount 或其他单词，这体现了命名的一致性。

    @property (readonly) NSUInteger count;

  4. 杜绝过度缩写，严禁自创缩写。你明白这个缩写的意思不代表其他人也一定会明白，你的代码可能会被任何人阅读，而阅读的人来自不同的地方接受不同的教育不同的文化，所以建议一般不要乱使用缩写，只使用那些国际通用缩写。如果为了缩写创建一个缩写对照表只会增加代码阅读复杂度。正例：setBackgroundColor，反例：setBgColor。

  5. 方法名、属性名等一些非全局命名遵循首字母小写的驼峰命名方式命名。

  6. 成员变量需要以 _ 开头。比如：NSString *_nameString;

  7. 如果模块、接口、类、方法使用了模式，在命名时尽量体现出具体模式。比如：LoginProxy。

  8. 所有类，方法，属性等，做到见名知意，采用驼峰式命名。

类命名

应该用大写开头的大驼峰命名，类名中必须包含一个名词来说明这个类是做什么。例子：ZKRLoginViewController。

方法命名

注意点：

  • 所有方法名称禁止以 new 开始。
  • 所有方法名称禁止使用 _ 开始。系统会使用 _ 开头命名一些系统私有方法。
  • 小驼峰法命名 arrayWithArray:(NSArray *)array。
  • 建议：内部私有方法需要增加前缀，前缀需要保持唯一性（x_）。给私有方法加前缀有 2 个好处：1. 增加辨识度，提高代码可读性；2. 避免自己的方法无意间覆盖了系统/框架同名的私有方法。

细则：

  1. 如果方法返回接收者的某个属性值，请直接使用属性名作为方法名。比如：- (CGFloat)cellHeight
  2. 如果方法间接返回一个或多个值，使用 getXxx。
  3. 参数之前的单词尽量能描述参数的意义。比如：- (id)viewWithTag:(NSInteger)aTag;
  4. 方法的每个参数前都必须添加关键字。正例：- (void)sendAction:(SEL)aSelector toObject:(id)anObject；反例：- (void)sendAction:(SEL)aSelector :(id)anObject :(BOOL)flag;

类别命名

注意：Category 中尽量不要声明属性，能挪尽量挪到主类中声明。尽管从技术上来讲可以在分类中声明属性，但是这么做需要格外小心，因为它很容易出现内存上或其他一些问题，而且一旦出现问题很难排查。

格式：类名+标识+扩展。比如：UIImageView+ZKR+Wep -> UIImageView+ZKRWep（wep：扩展功能，zkr：标识）。

Protocol 命名规范

规则：以触发消息的对象名开头，如果它没有关联任何类则可以忽略这个规则。比如：- (BOOL)application:(NSApplication *)sender openFile:(NSString *)filename;

常量命名

解释：常量（宏定义，枚举，局部常量等）。

  1. 宏定义：#define kScreenWidth

  2. 枚举：

    typedef NS_ENUM(NSUInteger, ZKROrderType) {
    kZKROrderTypeNone = 0,   // 无
    kZKROrderTypeFinish = 1, // 已完成
};

  3. 常量：const CGFloat kAnimationDuration = 2.0;、const CGFloat UIActivityIndicatorViewAnimationDuration = 2.0;

Notification 命名规范

格式：Notification 的命名风格由「类名前缀」+「通知事件名称」+「Notification」3 个部分组成。比如 UIApplicationDidBecomeActiveNotification：UIApplication 表示该通知属于谁，DidBecomeActive 表示该通知的作用，Notification 表示它是一个通知。

图片命名规范

规则：文件名全部小写；采用 _ 连接单词；命名风格为「标识_模块_属性描述」，可根据项目适当增加描述。比如：zkr_mine_scan。公共类建议使用方法。

二：编码规范

通用编码规范

  1. 禁止使用过时的方法或类，应该及时去了解和使用新方法或类。

  2. 有警告的，必须要消除。

  3. if、else、for、while、case 等后面必须要有 {}，除非后面是简单的 return 类型语句，例如 if (xxx) return;。

  4. 声明常量请使用 const 类型声明，禁止使用 #define 宏定义。

  5. 一些公共方法时，请尽量使用内联函数或者全局函数而不是宏定义。

    CG_INLINE NSBundle* kZLBnBundle() {
    return xxx
}

    函数不通过对象调用，所以不会走 OC 的消息转发流程，效率远高于方法调用；而且函数会有返回值和参数类型以及参数检查，而这些都是宏定义没有的。

  6. 不可变对象尽量使用 copy 修饰，如果重写使用 copy 修饰的 set 方法，请注意调用 copy 方法。

  7. 单行字符数限制不超过 150 个，单个类代码行数不得超过 800 行。

  8. 头文件中不要声明成员变量而是使用属性代替。

  9. 头文件中的属性尽量声明为只读，可以在实现文件中再将属性声明为可读可写。

  10. 如果大括号内为空，则简洁的写成 {} 就行。

  11. 没有必要增加多余空格来使上下代码的等号对齐。

  12. 少用 if else，可以使用 if return 替换，if 嵌套最好不超过 5 层，可用 switch。

  13. 头文件中尽量少引用其他头文件，尽量使用 @class 向前声明，每次引入其他头文件时问问自己是否必须要这样做。

  14. 使用不可变字典的同时，一定要注意安全判断，最好使用可变字典赋值参数。

  15. 相同的逻辑方法避免在多个地方出现，尽量封装成公共类。

  16. 及时删除因更新优化功能废弃的代码、文件，并且不要大片注释未被使用的代码。

  17. 不允许直接使用数字代表事件类型。

Block 编码规范

  1. 调用 Block 必须判空处理。比如：self.block ?: self.block();

  2. 在 Block 内部使用外部变量时要注意循环引用的问题。如果 Block 内部使用了 strong 修饰了外部的 weak 变量，那么当使用 strong 指向成员变量时需要进行判空，否则会崩溃：

    __weak typeof(self) weakSelf = self;
cell.refreshTableViewBlock = ^{
    __strong typeof(weakSelf) strongSelf = weakSelf;
    if (strongSelf != nil) {
        strongSelf->_name = @"name";
    }
};

    如果把 strongSelf != nil 的判断去掉那么可能会崩溃。方案二：如果项目中有 RAC 框架的话，在 block 前增加 weakify(self); 在 block 里面使用 strongify(self);。

  3. 类中有多个回调方法，不能使用 block，改成 Delegate。

代码结构规范

  1. {} 括号：

    - (void)configUI {
    xxxx
}

  2. 方法和属性：- (void)configUI { 注意空格位置；@property (nonatomic, assign) BOOL flag; 注意空格位置。

  3. 代码块 #pragma mark -Xxx：

    • #pragma mark -Cycle Life 生命周期
    • #pragma mark -Action 点击事件
    • #pragma mark -UI 创建 UI
    • #pragma mark -Public 公开方法
    • #pragma mark -Private 私有方法
    • #pragma mark -XxxDelegate 代理
    • #pragma mark -Common 等

  4. 不同逻辑、不同语义、不同业务的代码之间插入一个空行分隔开以提升可读性：

    [self createSubviews];
[self createTableview];

[self netRequest];

  5. @property 同一类型的声明放在一块，不同类型的声明用 2 行空行隔开：

    @property (nonatomic, strong) UIView *headView;
@property (nonatomic, strong) UITableView *tableView;


@property (nonatomic, copy) NSArray *dataSourceArray;

注释规范

  1. 添加必要的注释，按系统注释风格来。
  2. 所有 .h 文件中的 property（属性）需要给出注释。
  3. 所有自定义的方法需要给出注释。
  4. 比较大的代码块需要给出注释。
  5. 程序中出现加密/解密逻辑的地方，需要给出注释说明过程。
  6. 注释不要写的太冗长，要简单易读容易理解。
  7. 别给糟糕的代码加注释——重构它。
  8. 当修改了方法实现时需要同步修改注释内容。

通知编码规范

  1. 在发送通知时，请使用 userInfo 进行传值，而不是 object。
  2. 通知中心是以同步的方式发送请求的，所以不要在通知方法做一些复杂的计算，特别是当它处于主线程的时候，如果想发送异步通知可以使用 NSNotificationQueue。
  3. 在工程里能不用通知尽量不用通知。通知虽然灵活强大，但是如果滥用会导致工程质量下降，出现问题时也比较难排查。

三：图片使用规范

  1. 现有图片分为普通图片和 gif 图片；部分页面需要将 gif 转为 png 图片显示；方法使用阿里云提供的方法，项目中已经在 NSString 的分类方法中添加，例：[url checkAndChangeGifUrl]。

  2. 普通图片加载预处理，使用阿里云提供的方法进行预处理，以到达压缩图片、减小图片加载内存占用、提升加载速度的目的。处理方法：

    ZKRUrlCropAliyunImageWidth(NSString *originImageUrl, CGFloat width)
ZKRUrlCropAliyunImageSize(NSString *originImageUrl, CGFloat width, CGFloat height)
ZKRStringCropAliyunImageSize(NSString *originImageUrl, CGFloat width, CGFloat height)

    方法改变图片尺寸，并且转为 webp 格式图片，第二个参数用显示控件的尺寸 *3 或者适当放大；此方法仅处理 png、jpg、jpeg 格式图片；返回分为 NSURL 和 NSString。注意：超过 20M 的图片处理不了。

四：包体规范

  1. 使用 tinypng 压缩 png 图片，视频可以通过 Final Cut 等软件进行分辨率压缩，音频则降低码率即可，json 文件压缩处理。
  2. 大于 100Kb 的必须放远端，特殊条件除外。
  3. 非必要资源文件可以放到服务器上。
  4. 图片资源文件放入 Images.xcassets 中。Images.xcassets 中的图片在加载后会有缓存，可以提升加载速度。
  5. 优化重构代码，必须删除之前文件和资源文件。
  6. 资源太大，必须让设计处理，无法沟通上报。
